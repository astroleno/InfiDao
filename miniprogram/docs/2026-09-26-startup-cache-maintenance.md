# 启动缓存回收与存储降级

## 原因与边界

每次冷启动创建新的经文链，旧的经文链和窗口快照一直留在 `chain-store` 中。达到应用设置的 3 MiB 预算后，首次保存失败，页面无法进入经文流。临时阅读解决了启动阻塞，但不能单独解决缓存增长。

本次仅修改原生经文链缓存、启动提示与回归测试。个人注脚是包含原句、出处和用户文字的独立记录；API Key 也独立存储，两者不属于可回收缓存。系统文字继续使用简体，流动主视觉不变。

## 模块与接口

- `createChainStore` 增加可选 `autoPrune`，页面启用；默认严格保存语义不变。
- 本次页面会话访问或保存的经文链保护其整棵树：父链、兄弟分叉、历史窗口一起保留，仍可按原位置返回。
- 只回收之前会话的缓存树，按最后保存时间从旧到新整棵删除。平时最多保留两棵未使用的旧树；接近容量限制时继续回收，为本次写入留出空间。旧版本没有时间戳时按索引插入顺序处理。
- 不同 provider 的缓存前缀分别管理。不会调用 `clearStorage` 或删除前缀之外的记录。
- 首次写入核对本前缀的索引和实际键：去掉缺少文件的索引项，回收中断写入或中断清理遗留的孤立缓存。
- 清理先提交缩小后的索引，再删除旧缓存文件。索引写入失败不删文件；文件删除中断，下次写入或启动重试。
- 本机写入失败时，回收可用旧缓存并重试一次。没有可安全回收的空间时，仍可进入有界的临时阅读，明确提示本次进度不落盘。当前整棵树及注脚不会为了腾空间而被静默删除。

## 验收

1. 连续冷启动 300 次，持久缓存保持有界，不因旧会话累积而进入临时模式。
2. 至少 30 次分叉后，父链、兄弟分叉、历史窗口均可返回。
3. 存储预算满、实际写入配额失败、索引写入失败、清理中断及孤立缓存均有回归覆盖。
4. 自动清理不触碰个人注脚、API Key 或另一个 provider 的缓存。
5. 模拟器在已有满缓存的条件下冷启动，确认正常流动、持久保存与再次启动；真机成绩单独核验。

这里的保证是旧缓存不再无限累积并阻断启动。设备存储始终不可写，或当前受保护会话自身超出预算时，仍会明确降级，不能承诺任意长历史都永久保存。

## 实际验证

开发者工具已有的满缓存经自动回收删除了 177 条旧经文缓存，保留 3 条记录，预算计量为 79,128 字节。页面恢复 `phase=flow`、`running=true`，`temporary=false`，`glError=0`；这次已恢复持久写入，不再依赖临时模式。未执行全量清缓存，也未修改连接设置。这是模拟器结果，手机需更新预览包后核验。

再次冷启动后自动回收 1 条旧记录，仍保留 3 条，`temporary=false`，经轮继续运行。待提交版本单独导出验证，全部 123 项原生测试通过，包括 300 次冷启动、30 层分叉、存储失败及清理中断的回归。
