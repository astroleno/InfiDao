# 经文为主、由解释分出新经文链 · 设计提案

日期：2026-09-22。

状态：用户已确认产品关系；以下模块、接口与验收为待确认提案。本文件不替代现有 DESIGN.md 中已批准的视觉设计，不代表已实现或已获线上发布授权。

## 1. 已确认的产品关系

用户明确：**经文主体，解释与联系作为附加；可以从解释和联系中的单个入口，跳到另一条新的经文链。**

- 经文始终占据主要视觉空间。解释帮助理解当下这一句，联系帮助选择接下来往哪里读。
- 点词后的主要结果是一条新的经文链。新链仍呈现经文、短解和可点击入口，并可再次分叉。
- 新链保留来源：从哪条链、哪句经文、哪个字词进入。返回时恢复原链的原位置。
- 初始一念是背景；用户点击的字词成为新焦点。既保留语义承接，也允许用户主动转向。
- 保留现有黑场、竖轴经轮、字体、玻璃与色散方向。解释与联系不进入经轮字形纹理。

## 2. 当前实现与参考的边界

- 当前小程序的 `flow/provider.js` 只提供三组本地精选示例，每组八段；它尚未连接网页端检索或 DeepSeek。
- 当前解释只能在停驻后看到，解释文字和联系尚不能触发新链。
- `ref/infinite-wiki` 按英文空白拆词；点词会清空当前页面，再请求一段定义。中文需要明确的字词语义边界，不能直接搬用该拆词方式。
- 网页端已有 11,829 段本地原文及出处，但现代语义召回的冻结测试未通过。在线版本不能直接把该召回结果当作已满足本产品质量要求。
- 当前字体覆盖 665 个字。调查起始版本的图集约容纳 100 个不同字符；同一工作区正在将其改为按设备容量自适应。开放内容仍需要字体覆盖和图集窗口管理，实施时复用这轮改动，不重复重做。

实际参考：本项目 `miniprogram/docs/DESIGN.md`、`miniprogram/flow/provider.js`、`miniprogram/pages/flow/index.*`，以及 `ref/infinite-wiki/App.tsx`、`components/ContentDisplay.tsx`、`services/geminiService.ts`。没有读取相邻项目或私人历史。

## 3. 阅读与分叉体验

### 正常流动

1. 当前经文在经轮中成为焦点；上下相邻经句继续构成主画面。
2. 附加区跟随当前完整经句，呈现一条短解和少量联系。长句拆成两圈时，附加内容仍绑定同一完整经句。
3. 短解建议 25–50 字；可见入口通常 2–3 个，支持有独立意义的单字、词和短语，例如「止」「定」「本末」「与人相处」。这些数量是阅读密度建议，不是递归层数上限。
4. 附加区采用原生文字，位于不与 Canvas 触摸区域重叠的区域；优先复用现有下方阅读区，具体高度以真机可读性确定。主经文的字号、字体和五层关系继续沿用已确认方向。
5. 下一条未准备好时，当前经文仍可读、可点、可回看；不给用户展示空白页，也不自动循环同一批经文冒充新内容。

### 点击入口

1. 按下入口时锁定当前经句及入口身份，并立即给予轻微视觉反馈；内容随流动更新也不能改变这次点击的含义。
2. 保存原链当前段落、经轮位置、阅读区位置、流动/停驻状态和当前路径。
3. 准备新链首句；旧经文持续留在画面中。缓存或预取命中时直接进入承接动画。
4. 新经句接替中心焦点，沿新方向继续流动。附加区出现其短解和新的分叉入口。
5. 轻量显示「由『本末』而来」及「返回原链」。完整路径按需查看，不常驻一棵占据阅读空间的树。
6. 返回原链直接恢复保存的位置和内容；不重新生成、不自动跳到链头。改点原链的另一个入口，会创建或恢复另一条支链。

经句本体继续支持停驻、原文和前后段阅读。点解释或联系不会额外要求先点一次「停驻」。用户回看、触摸阅读或打开原文时暂停自动推进；明确继续后恢复。

### 内容示例

以下解读仅为交互样例，原文引自项目本地语料。

- 初始一念：总想一口气把所有事情做好。
- 主经文：**知止而后有定，定而后能静。**（《大学》，`rysxguji-daxue-1-2`）
- 附加短解：先辨明值得抵达、守住的方向，心才有定向。放在眼前的事情里，也可以先理清「本末」。
- 点击短解中的「本末」→ 新链以 **物有本末，事有终始。** 开始（《大学》，`rysxguji-daxue-1-3`）。
- 新链短解中的「先后」仍可点击；下一条经文及后续链须由真实候选验证后提供。样例不把尚未准备的分支标记为已可用。

句意与当下应用保持区分。例如「知止」保留应当抵达、安住于何处的方向性，不能只解释成停止行动；联想可以启发阅读，但不能当作经典本义或文献之间存在直接传承关系的证据。

## 4. 内容层：短解、入口和新链一起准备

- 原文层：服务端从本地语料返回原文、出处、段落 ID、文本版本及引文范围，模型不能自行编造出处或改写原文。
- 短解层：围绕当前经句和当前焦点，生成一小段可直接读的解释，避免每次输出长篇议论。
- 入口层：返回结构化文本片段和稳定的入口 ID。单字也必须有当前语境，例如「定」在这里的意义，而非仅将裸字发给模型。
- 链条层：每个入口绑定一个方向和真实候选经句；新链的首句须与入口语义相符，后续经句继续围绕这个方向。
- 语义层：优先准备经句的白话释义、概念与候选关系索引，补强现代语言召回；不能继续完全依赖手工别名。首句相关性和经句间联系需独立验证。
- 同一段原文的另一截引文不自动算作新的语义分支；在候选不足或没有证据时明确止于当前内容。

建议先使用 DS V4.1 Flash 承担候选语义判断、短解和入口组织。单次请求尽可能完成一个阅读节点的相关工作，避免逐次串联意图分类、选句、解释、生成链接。Jev 保留为以后对同一候选集的速度/质量对照，不新增到本次必经调用链。

## 5. 速度来自提前准备和小步更新

- 首屏可使用已验证的本地经句快速进入；具体一念的在线匹配与短解到来后，按阅读边界承接，不覆盖正在读的句子。
- 当前链始终争取保有后续 2–3 个已准备节点；实际点击比预取优先。
- 只预取当前可见入口中最可能使用的 1–2 条新链首节点。预取深度为一层，不递归生成所有子孙分支。
- 总并发初始预算为 2：前台至多 1 个，后台至多 1 个；前台需要资源时取消或让出后台请求。后台、回看、切换一念、卸载时停止无关预取。
- 缓存键包括原文版本、当前焦点、父节点、入口义项、提示词版本及模型版本。相同字词在不同上下文不能误用同一份个人化解读。
- 网络分块先经过 UTF-8 与消息边界缓冲，再解析完整事件；解释按完整短句或文本片段提交。已经展示的入口不因后续字到来而移动或改变目标。
- 合并原生数据更新，建议以 80–120 ms 为初始合并窗口，只更新变化的片段；不逐 token 更新整条阅读历史。
- 经轮仅维护可见经句和少量邻句的图集。点附加入口不为解释重建图集，也不在每次字词交互时重复执行截图承接。
- 阅读历史按链和节点保存；原生视图只挂载邻近节点，历史按需恢复。会话数量、缓存容量、网络请求和字体资源均有明确预算，不能随分叉指数增长。

DeepSeek 官方当前调用名为 `deepseek-flash`。低延迟请求显式使用 `thinking: { type: "disabled" }`，不能仅凭产品模式名称为 fast 就认为已关闭思考。这个选择与短解释字数共同接受内容质量验证。

## 6. 模块和关键接口提案

| 模块 | 职责 |
| --- | --- |
| `miniprogram/pages/flow/index.*` | 经文主体、附加区、入口点击、分叉承接、返回原链；只组合状态，不承载网络调度细节 |
| `miniprogram/components/flow-notes/`（新增） | 原生短解和联系片段，稳定的入口命中范围与无障碍描述 |
| `miniprogram/flow/chain-store.js`（新增） | 链、节点、父入口、当前位置、历史及恢复；分叉不改写原链 |
| `miniprogram/flow/continuation.js`（新增） | 下一节点缓冲、预取优先级、取消、请求去重与过期响应隔离 |
| `miniprogram/flow/provider.js` | 保留唯一内容入口，增加 branch/next；精选内容与在线服务共用结构 |
| `miniprogram/flow/remote-provider.js`（新增） | 原生网络请求、分块消息解码、超时、错误与取消；不保存模型凭证 |
| `miniprogram/flow/atlas.js`、字体模块 | 当前经句窗口、字形缓存、动态经文用字覆盖和资源释放 |
| `src/lib/flow/`、`src/app/api/flow/route.ts`（新增） | 复用现有 Next.js 服务端的原文资源，提供独立的经文链服务、语义候选、模型调用和数据校验 |

建议复用当前 Next.js 服务端，暂不引入第二套云函数后端。已有 `/api/search` 与 `/api/annotate` 的调用方继续按原合同工作；新小程序链路使用新增接口，涉及共享检索调整时另行覆盖其回归验证。

Provider 的操作：

- `open(seed)`：创建最初经文链。
- `branch({ chainId, fromFrameId, anchorId })`：按服务端可验证的父节点和入口创建或取回新链。
- `next({ chainId, cursor })`：分批取得后续节点；批次大小不等于整条链的最大长度。
- 每个操作提供取消句柄。结果携带请求标识和链版本，迟到结果不得替换用户已经进入的新链。

链包含 `chainId`、`parentChainId`、`entry`、`focus`、`frames`、`cursor`。经文节点包含 `frameId`、`sourceId`、`quote`、`source`、`meaning`、`reflectionSpans` 和 `anchors`；文本片段以 `{ text, anchorId? }` 表达，入口包含标签、当前义项和关系方向。出处取自原文库。

网络提案为 `POST /api/flow`，操作分别为 open/branch/next。返回可校验的 head/frame/done/error 事件，先让可信的首句可读，再补齐附加内容。微信端使用支持的分块请求；不支持分块时回退完整响应，业务数据结构一致。正式部署前必须确认实际网关不缓冲分块响应。

## 7. 验收标准与待测目标

以下延迟是拟定目标，不是本次已测成绩。

| 维度 | 验收 |
| --- | --- |
| 经文主体 | 五层经轮、已确认字体和色散关系保留；附加内容不遮挡中心经句，不引入额外必点页面 |
| 分叉 | 解释字词及联系入口均能进入新经文链；新链仍可继续分叉；单字入口按所在语境解释 |
| 连续性 | 连续分叉至少 30 次；可多次返回任意保存的父链；返回恢复位置和内容；链总长度不受八段批次限制 |
| 交互响应 | 入口触摸反馈 P95 ≤ 100 ms；已预取新链首句可读 P95 ≤ 500 ms |
| 未命中缓存 | 在约定真机和网络条件下，新链首句可读 P95 目标 ≤ 2.5 s；延迟期间原句可读且可取消，不用首 token 时间代替完整可读首句 |
| 引文 | 所有原文、出处、段落 ID 和引文范围均可校验；样例、句意、生成解读来源清楚 |
| 语义 | 独立标注的至少 30 个入口上下文，首句相关率目标 ≥ 90%；专门覆盖单字多义、跨典籍和“无适合分支”，不得把结构合法当成语义正确 |
| 状态与性能 | 连点、重复点、切一念、回看、后台、恢复、弱网、过期响应均不串链；固定并发和预取预算；连续阅读无图集溢出或不断增长的挂载节点 |
| 字体 | 动态经文用字覆盖经过验证；经轮不能因新内容静默变成黑体；缺字和字体请求失败保留可读降级 |
| 平台 | 微信开发者工具原生验证，并验证 iPhone 与 Android 真机；截图与操作记录不能用浏览器预览代替 |

## 8. 执行顺序与授权边界

确认本提案后：先与当前正在迭代的经轮、触控、图集和阅读层合并到同一实现基线，再完成小程序分叉、返回与预取机制，用可追溯精选链验证交互；随后接通本地服务端、真实模型、语义候选和动态字体，完成真实链路验证。精选内容是测试载体，不能以其代替最终在线能力验收。

实现批准不自动包含提交、推送、上传或发布。远程部署时需要确定正式 HTTPS 服务地址、微信合法域名和完整字体的授权供给；本次设计调查未调用付费模型、未修改应用代码、未读取模型密钥。
