# Flow 30 FPS 分析：技术核对与证据边界

日期：2026-10-23，按用户要求修订。执行入口：[统一优化方案](../plans/2026-10-23-001-fix-flow-60fps-execution-plan.md)。

## 1. 当前结论

网页绘制路径没有 32ms 限帧。当前测量条件存在约 30Hz 的绘制节奏；新文字首次生成和部分安全范围已优化，普通模式仍有明显停顿。旧候选长历史秒级间隔在本轮新旧构建上均未复现，不能认定根因已修复。具体瓶颈仍需同版本分阶段测量。

稳定 60 FPS 尚未通过；不承诺修改几个条件即可达标。默认入口、候选效果、GPU 字形缓存是不同概念，诊断必须分别记录。

## 2. 证据版本与口径

| 资料 | 可使用的事实 | 不能推出的结论 |
| --- | --- | --- |
| 最终 retained-render 构建 e3d8aa14afe348a3 | 短内容约 29 FPS，长历史存在约 1 秒间隔；结构缓存已经生效 | 普通 current 路径导致候选这组低帧率 |
| 最终极简控制 29.69 FPS | 当轮不能验收 60Hz | Ego 恒定锁 30，或环境不可改变 |
| 历史应用内浏览器静置三轮约 60 FPS | 旧版本静置 21 FPS 不是恒定值 | 最终构建快滚已达 60 FPS |
| 历史宽屏 20.81 / 手机视口 59.99 FPS | 不同条件出现显著波动，像素范围值得研究 | 像素吞吐已被证明是唯一原因 |
| 中间构建 GPU 静置 6.565–18.786ms / 滚动 9.105–15.806ms | GPU 工作不可忽略 | 当前最终版 GPU 仅 3–5ms，或已经接近极限 |
| 显示链 60.006Hz / FramePresented 29.404Hz | 浏览器显示链事件节奏不同 | 事件无页面归属仍可当作阅读器实际呈现 |
| 历史 96 组零像素差 / 最新 13 组最大差 1/255 | 各自限定修改与冻结基线的回归结果 | 任意后续降频、缓存或新动效已获画质认可 |

CPU 回调耗时不含完整浏览器工作；GPU 查询与 CPU 工作存在流水关系，不能简单相加。纹理采样数量不能直接按 TFLOPS 换算实测 GPU 时间。不同构建、模式、视口与轮次不得合并成一条因果链。

## 3. 四项过时诊断的修正

### 3.1 每帧遍历全部历史：已不成立

FlowStream 持有 StreamSceneIndex，查询可见段落和文字，并处理仍活动的段落。180 段、9630 个单元的诊断最多可见 155、索引访问 323。

仍需调查的是布局变化时 remeasure 的全量几何读取，以及 DOM 保留后的浏览器绘制/合成成本。它们与每帧全量遍历不是同一个问题。

### 3.2 悬停清空字体图集：已不成立

StreamFramePlanner 仅在真实 font 失效时增加字体版本。交互使用独立失效原因；StreamGlyphCache 依据字体版本和密度失效。

焦点拆行后首次出现的分数像素字形变体仍可能补充栅格，但不是清空全图集。

### 3.3 源范围只增不减：需区分容量与有效范围

StreamGlass.fitSource 计算本帧可收缩的 activeRect；planTargetRegion 分开 capacity 和旧新并集 dirtyRect。分配容量保留是避免反复分配的设计。

后续透射、湿边、曲面及水膜的有效影响范围还未全部完成安全优化，不能把“源范围已经分离”写成“所有光学范围已经优化”。

### 3.4 缓存满全清：已不成立

reserve 按旧单元回收并保护当前帧 pinned 单元，最多两页图集；CPU 字形位图另有 16 MiB 预算与回收。超出可见预算时按既有错误/回退处理，不无限扩容。

真实字体变更、密度变化及上下文恢复仍需要适当失效，这与容量满导致全清不同。

## 4. 仍成立的优化线索

### 4.1 首次生成行缓存的同步像素工作

本轮开始时 cell 路径包含两次整块 getImageData、逐像素处理和纹理上传；现已用原生覆盖合成去除两次读回和像素循环，只保留首次解析 CSS 颜色的 1×1 读取。新增可选 CPU 阶段诊断，明确嵌套计时不可相加。

同轮桌面首次快滚 CPU P95 从 13.3ms 到 4.3ms，重复快滚从 3.5ms 到 3.3ms（U2 中间构建，最终版首次为 5.0ms，非性能验收）。本轮前后电源状态不同且切换时刻未知，差值不可完全归因于代码。图像和内存预算保持；预备队列没有加入。最终构建及后续检查见[执行记录](../qa/2026-10-23-flow-60fps-execution.md)。

### 4.2 滚动仍触发较大范围合成

基础字形 key 不含绝对滚动坐标，已可复用；滚动却真实改变离焦、透明度、位置及前景归属。因此行字形命中不代表行模糊或整张玻璃结果可复用。

优化应进一步减少无变化的描述、上传与无影响像素；不能把所有滚动都改成 sourceChanged=false。原架构方案的更新矩阵明确要求更新受影响合成。

### 4.3 普通模式仍采用 Canvas 文字源

shape.liquid 的门控使普通 current 不使用 GPU 字形缓存。普通路径的 fillText/filter 与源纹理上传值得独立测量。

最终候选桌面 891 帧、手机 884 帧均为 cached，旧 Canvas 4 字节；该门控不是这些低帧率的原因。解除门控还需支持普通手机最大 9px 模糊，现 GPU 前景支持到 8px；不能降规格强行进入 GPU。

### 4.4 长历史仍有独立问题

上一轮最终候选长历史 trace 出现 5 次超过 500ms 的 BeginFrame 间隔，同期定时器继续运行。本轮最终普通模式目标页面 trace 出现 4 次超过 500ms 的间隔，单次主帧最长约 25.8ms。记录不足以把整段间隔归因于 JS、布局、GPU 或操作系统中的任意单一环节。

本轮已记录重布局原因、次数和耗时，合并同帧字体/尺寸通知。新旧构建的同轮长历史候选诊断均约 29.5–29.7 回调 FPS，未复现旧轮次秒级间隔；不能据此认定根因已修复。普通模式仍有明显停顿。读写相间本身不能证明每个词都强制一次布局；透明 DOM 是否额外栅格也需失效追踪。

### 4.5 光学范围尚有工作

本轮把 activeWidth 与纹理容量映射分开，用于源绘制和水膜横向 scissor；水膜仅绘制两侧折叠带，中央使用 shader 原有的精确中性色。保留边界保护像素、原分辨率和每帧相位。后续透射和最终曲面的安全范围仍未证明，继续完整绘制。GPU 分通道计时有超时及归因限制，不能选定唯一主内核。

不能拿估算的全屏采样数当实际执行数，也不能预先承诺节省 50–90%。

## 5. 动态质量与产品边界

- liquid-live 的持续动态是既定效果；静置仍更新水膜不等于无效工作。
- 现有双相位插值针对缓慢变化的接触遮罩；几何、法线、折射、焦散仍使用每帧当前相位。将整个水膜降到 30Hz 需新的连续画面等价证据。
- 0.5px 模糊量化、删除背景模糊、中心文字改由 Canvas 全权代画都不能直接保证原画质和原生行为。
- 噪声散列纹理已有条件上传；仅格点或整相位改变时更新，并非静置每帧重传。
- “新增每行入水进度”是动效设计扩展；候选默认关闭是明确约束，不是缺陷。

## 6. 执行与验收

按统一方案 U0–U6 推进，不再维护第二套工期或收益估算。先冻结基线，随后校准控制、分模式采样与分阶段定位；对有实测依据的成本逐项优化。

每个修改需通过相应单测、类型、lint、生产构建及画质/交互回归。正式验收覆盖 30 秒 × 5 轮、归属明确的实际呈现与异常轮次。手机视口模拟不代表真机通过。
