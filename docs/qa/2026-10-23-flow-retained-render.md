日期：2026-10-23。对应[已批准的渲染架构方案](../plans/2026-10-23-flow-60fps-render-architecture-research.md)。

**状态：结构修正已实施，画质和已列交互检查通过；稳定 60 FPS 未通过，整个性能目标尚未完成。**

完整页的最新短内容诊断约 29 FPS；长历史仍出现约 1 秒的间隔。控制页未达到 60 Hz 绘制节奏，且部分长历史复测发生焦点变化。既不能把绘制代码的 CPU 下降当成整页达标，也不能把全部问题归因于环境。

## 4. 画质对照

最终版本固定字体、相位、文本、视口和逐字进度，对照冻结基线。13 组覆盖手机/桌面边缘文字、部分显现、高亮、移出与返回、零显现、中央释义、源范围扩大后收缩，以及原模式 → GPU 候选切换。

| 指标 | 13 组结果 |
| --- | ---: |
| 最大单通道色值差 | **1 / 255** |
| 单组最多不同像素 | **6** |
| 非黑局部区域 MAE 最大值 | **0.0000269 / 255** |
| 基线亮像素在新版完全消失 | **0** |

MAE 的分母使用两图非黑区域并集，避免被全屏黑底稀释。基线亮像素阈值为 RGB 最大值 >8；“消失”指对应新版 RGB 全为零。它是诊断指标，不能单独排除所有视觉问题。

已查看完整阅读页、逐字显现对照和区域收缩图片，没有观察到裁切、残影、笔画丢失或光学效果降级。早期 15 组系统衬线字体及焦点拆行对照也保留，最大差值 3/255、最多 16 个像素；它们不替代最终康熙字体结果。

`gl.readPixels()` 仅用于这些固定画质对照。帧率测量未插入 `gl.finish()` 或像素读回。

### 6.3 缓存与内存边界

| 项目 | 结果 |
| --- | --- |
| 桌面重复快滚 | 栅格化次数保持 472，行失配保持 69，分配次数保持 16。 |
| 手机模拟重复快滚 | 栅格化次数保持 260，行失配保持 90，分配次数保持 16。 |
| 后续长历史重复快滚 | 栅格化次数保持 411，行失配保持 43，分配次数保持 16。 |
| 字体失效 | 同一稳定测量内保持 1；悬停、追加与反复滚动不会清空字体图集。 |
| CPU 字形缓存 | 预算 16 MiB；超出预算按旧单元回收。 |
| GPU 字形图集 | 最多 2×2048×2048 RGBA8，即 32 MiB；不把满图集整体清空后重建。 |
| 行/度量记录 | 行缓存有上限，度量最多 2048 项。 |
| GPU 成功路径旧 Canvas | 仅 1×1 度量画布，4 字节；从原模式切回后也回到此值。 |

这些字节数是代码管理资源的容量记账，不是操作系统测得的总显存。旧 Canvas、JS 对象、原生 DOM、浏览器内部纹理等不能混为同一个显存指标。重复快滚仍有必要的顶点和动态水膜上传；“没有新增栅格化”不等于“没有任何上传”。

焦点导致分组变化时，某些分数像素栅格原点首次出现仍需补字形变体，以保持原来的抗锯齿。测试证明不会清空字体图集，不能笼统声称所有高亮首次切换都绝对零栅格化。

## 7. 控制实验与 GPU/呈现追踪

### 控制页

不运行阅读器，仅让 160×160 Canvas 每个 RAF 交替颜色。早期控制分别约 7.21、10.49、29.10 FPS；恢复浏览器验证空间后 8 秒约 29.38 FPS，间隔中位数 33.3 ms，最大 166.2 ms，当时可见并获得焦点。

最终控制记录为 `final-control.json`：8 秒、239 个回调，**29.69 FPS**，间隔中位数 33.3 ms、P95 34.3 ms、最大 50 ms；逐回调检查的失焦和隐藏次数均为 0。控制未通过 60 Hz 校准。因此没有把这些 10 秒诊断包装为方案要求的每场景 30 秒 × 5 轮正式验收，也没有宣布“Ego 恒定锁 30”或擅自改变系统/浏览器全局设置。

### GPU 异步计时

16 个整段查询均检查 `GPU_DISJOINT_EXT` 和结果可用墙钟边界。静置样本约 6.565–18.786 ms，滚动约 9.105–15.806 ms。探针在绘制第一条 GPU 操作前开始，回调结束时结束，异步读取。

这些样本属于中间构建 `698931b41f8624f8` 的诊断。后续分通道查询出现明显波动，与整段测量不具备足够可比性，因此未将各次 draw 的时长相加，也未据此选定“最慢内核”后盲目重写原材质。主要 GPU 成本尚未可靠归因。

### 浏览器呈现链路

仅记录图形类别且过滤参数的 2.5 秒 trace 中，显示链回调约 60.006 Hz，而 `FramePresented` 事件约 29.404 Hz。保存数据不含页面文本、URL、栈和截图；由于没有保留表面归属，事件统计属于浏览器显示链，不能认证为本阅读器的实际呈现 FPS。

最终构建的 7 秒长历史主线程 trace 用本页起止标记确定进程，只保存该进程的无参数事件：

- `BeginMainFrame` 42 次，单次最大 68.66 ms；`Layout` 最大 5.72 ms，`Paint` 最大 8.20 ms。
- `ExternalBeginFrame` 最大间隔约 1016 ms，出现 5 次超过 500 ms 的间隔。
- 同期定时器事件仍出现，最大间隔约 214 ms，没有超过 500 ms。

因此秒级间隔不能仅用一个长 JS 任务解释；GPU/合成/刷新调度仍需进一步定位。各类 trace 时长有嵌套关系，不能相加。数据没有证明所有长间隔都由操作系统导致。

## 8. 未通过项

1. **稳定 60 FPS 与屏幕实际呈现验收未通过。** 控制页条件不足，整页诊断也明显不达标。
2. **长历史快滚的秒级停顿仍未解决。** 可见性索引与稳定缓存已经生效，完整页面仍需要进一步定位和修复。
3. **首次新文字进入视口的 CPU 峰值仍高。** 不能只报告已预热路径。
4. **主要 GPU 内核及安全光学范围的后续优化尚未完成。** 没有可靠证据支持删采样或改变画质来换帧率。
5. **每场景 30 秒 × 5 轮、归属明确的实际呈现指标、错过刷新比例及真机手机验证未完成。** 没有用户同意延期，不记为完成。

这些是尚未完成的必要工作及验证限制，不是通过验收后的可选改进。
